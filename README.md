# 📊 AI-Driven Sales Forecasting System

An end-to-end machine learning and business intelligence project. It forecasts next-month
revenue for **185 stores** (one per country in the source data), checks the forecast against
honest benchmarks, and serves the results in an interactive **Streamlit** dashboard and a
**Power BI** report.

## Highlights

- **Leak-free pipeline.** Every feature for a month uses only earlier months, and the same
  code builds training rows and forecast rows.
- **Store segmentation.** KMeans groups stores into Low, Medium and High sales tiers. Models
  are trained per tier, with a single global model as a challenger. The approach with the lower
  hold-out error is used for the forecast.
- **Honest evaluation.** The model is compared with five simple benchmarks, not only
  "last month", on a 6-month hold-out period.
- **Forecast ranges.** Every store gets an 80% range, estimated from hold-out errors.
- **Reproducible.** One command rebuilds every processed file and model, and tests confirm the
  committed outputs match the code.

## Results

Hold-out period: Jan to Jun 2017 (6 months, 1,110 store-months). Models were trained on
earlier months only.

| Method | MAE | RMSE | WAPE | Monthly total error | MAE vs naive |
|---|---:|---:|---:|---:|---:|
| **Cluster-wise ML models (used)** | **$2,691,781** | $3,340,500 | 70.1% | **5.3%** | **+27.7%** |
| Store historical mean | $2,692,485 | $3,331,500 | 70.1% | 5.6% | +27.7% |
| Single global ML model | $2,693,205 | $3,328,880 | 70.2% | 5.3% | +27.7% |
| 12-month moving average | $2,795,445 | $3,471,788 | 72.8% | 5.7% | +25.0% |
| 3-month moving average | $3,037,588 | $3,828,577 | 79.1% | 6.9% | +18.4% |
| Naive (last month) | $3,724,815 | $4,739,317 | 97.0% | 8.2% | 0.0% |
| Seasonal naive (same month last year) | $3,775,944 | $4,827,694 | 98.4% | 7.3% | -1.4% |

*WAPE = total absolute error ÷ total sales. Monthly total error = mean absolute % error of the
all-store monthly total.*

**How to read this**

- The model's error is **27.7% lower than the naive "next month = last month" forecast**. Its
  all-store monthly total is within **5.3%** on average, and that total is the number revenue,
  stock and staffing plans depend on.
- It is **on par with a store's historical average**, not clearly better. Sales in this dataset
  barely depend on previous months: per-store autocorrelation is about 0 at every lag (see the
  notebook). The source file is a synthetic sample with randomly generated orders. Most of the
  gain over naive therefore comes from predicting a store's typical level instead of copying last
  month's noise. On real retail data with trend or seasonality, the lag and rolling features have
  more signal to use.
- Single store-months stay hard to predict (WAPE ~70%). Use the forecast ranges, not the point
  values, for store-level decisions.

## How it works

1. **Clean and aggregate.** Raw orders are summed into monthly revenue per store. Stray
   whitespace in country names is stripped. Months with no orders are filled with zero, so
   "last month" always means the previous calendar month. The final month (July 2017) is
   dropped because the raw file stops on 28 July. That month is forecast instead.
2. **Features.** Lags (1, 2, 3, 6, 12 months), rolling 3/6/12-month means, 6-month volatility,
   the store's historical mean, and month, quarter and year.
3. **Time-based split.** The last 6 months are held out. There is no random shuffling.
4. **Store tiers.** KMeans runs on each store's average, volatility and peak month, using
   **training months only**. Tier ids are ordered by sales, so 0 = Low and 2 = High on every run.
5. **Models.** A gradient boosting regressor is trained per tier, plus one global model, and both
   are scored with the benchmarks above. It uses squared-error loss on purpose: an
   absolute-error loss wins store-level MAE by about 2% but predicts medians, and that
   under-forecasts the monthly total by about 17%.
6. **Refit and forecast.** Models are refit on all months. Each store's forecast is built from
   the same feature code, and its 80% range comes from hold-out errors in its tier.

## Quick start

Requires Python 3.11+.

```bash
pip install -r requirements.txt

# Rebuild processed data, models, metrics and the forecast (~15 s)
python src/train_cluster_models.py

# Forecast again from the saved models
python src/predict_next_month_cluster.py

# Launch the dashboard
streamlit run app.py
```

Both scripts work from any directory. Useful training options:

```bash
python src/train_cluster_models.py --model rf         # RandomForest instead of gradient boosting
python src/train_cluster_models.py --strategy global  # force one global model
python src/train_cluster_models.py --clusters 4 --valid-months 12
python src/train_cluster_models.py --keep-partial-month
```

The dashboard loads the committed models. If they can't be used in your environment (missing
files, or a different scikit-learn or numpy version), it retrains in memory automatically.

### Development

```bash
pip install -r requirements-dev.txt
ruff check . && ruff format --check .
pytest
```

The tests cover data cleaning, leakage checks for features, feature parity between training
and forecasting, clustering, the full pipeline, a smoke test of the dashboard, and a check that
the committed models and outputs match the current code. CI runs them on every push and pull
request.

## Streamlit dashboard

- **Overview:** KPI tiles, monthly revenue with the forecast, forecast by tier and region, and
  top stores (forecast vs last month).
- **Store explorer:** any store's history with its forecast and 80% range.
- **Model performance:** the benchmark comparison above, with results by tier.
- **Forecast table:** the full forecast, filterable, with CSV download.

Sidebar filters (region, tier) apply everywhere. The dashboard supports light and dark themes.

## Power BI dashboard

Screenshots of the report are in `Project Working PowerBI Screenshots/`. The `.pbix` file is
not part of this repository. To rebuild it, load
`data/processed/next_month_forecast_cluster.csv`:

| Column | Meaning |
|---|---|
| `store_id` | Store (country name) |
| `region` | Sales region |
| `cluster`, `cluster_label` | Sales tier id and name (0 Low, 1 Medium, 2 High) |
| `date` | Last actual month |
| `last_month_sales` | Revenue in that month |
| `forecast_month` | Month being forecast |
| `forecast_sales` | Forecast revenue |
| `forecast_lower`, `forecast_upper` | 80% forecast range |
| `change_pct` | Forecast vs last month, in % |

> The earlier export used numeric codes (0 to 184) for `store_id`. It now holds the country
> name, and the new columns are additions. Refresh the data source in Power BI after
> retraining. Revenue in the source data is in US dollars.
